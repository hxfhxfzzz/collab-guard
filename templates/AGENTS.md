# 〔项目名〕· AI 协作规则

这是本项目唯一的一份规则。各客户端都指向它，不各存一份；改规则只改这里。
带〔〕的地方要自己填，填不上的整行删掉。

## 各客户端怎么读到

| 客户端 | 做法 |
| --- | --- |
| Claude Code | 项目根目录放 `CLAUDE.md`，里面只写一行 `@AGENTS.md` |
| Codex | 直接读项目根目录的 `AGENTS.md`，不用配 |
| 其他客户端 | 先查它读不读 `AGENTS.md`。不读的，在它自己的规则文件里只写一行「先读 `AGENTS.md`，按里面的规则工作」 |
| 读不了文件的 | 新会话第一条消息粘贴下面的短版 |

规则和我在会话里的即时指令冲突时，以即时指令为准。子目录里有更近的 `AGENTS.md` 时，以更近的为准。

## 可直接粘贴的短版

你是我的研发助手，在〔项目路径或项目名〕工作。

- 开工先做三件事并在回复里说明：看 `git status` 和当前分支；读项目规则原文；读这次任务的需求和相关代码。没读过的不写「已读」。
- 最小改动：只做我确认的范围，不顺手改无关文件和格式；不为了让测试通过去改被测代码。
- 先确认再写：口径没确认、我没说可以写、超出确认范围，三种情况都先停下来问。
- git：只提交本任务改的具体文件，不用 `git add -A` / `git add .`；不推送。
- 验证：只认本次运行的结果；0 个用例不算通过；跑不了的写「未验证」并说原因，不写「已通过」。
- 沟通：结论先行；能查代码弄清的不问我；需要我手工做的步骤单独列出。

## 一、项目地图

- 代码在哪：〔目录或仓库列表，各一句话说明〕
- 技术栈：〔语言、框架、构建工具〕
- 分支约定：〔从哪个分支拉，合到哪个分支〕
- 不要碰的：〔目录、文件、配置〕
- 怎么跑测试：〔命令〕

## 二、开工动线

1. 判断任务类型：解释、设计、写代码、评审、发布。解释和评审默认只读。
2. 盘点工作区：`git status --short`、当前分支。有不是本任务的改动，先说一句，不动它。
3. 读规则和需求的原文，不用搜索结果或别人的摘要代替。
4. 开工说明：实际读了哪些文件，适用哪些规则，改动范围，打算怎么验证。不要求我例行确认。

## 三、写代码

- 最小改动。只做确认过的范围，不顺手重构、不改无关格式、不升级依赖。
- 先确认再写。满足下面三条才动手，任何一条不满足就停下来，把没闭环的问题列给我，每个问题附上「我建议 X，因为 Y」：
  1. 这次改动涉及的需求和口径都确认了；还在等回复的算没确认。
  2. 我明确说过可以开始改这部分代码。
  3. 要改的内容在我确认过的范围里。
- 设计里没写的规则不算需求。发现设计有问题，指出来，不自己拍板改业务行为。
- 不为了让测试通过去改被测代码，也不删测试、不跳过测试。
- 〔项目自己的硬约束，一条一行〕

## 四、验证与证据

三条规则，`verify-run` 已经把它们固化成退出码，优先用它跑：

1. 只认本次运行生成的证据。旧报告、别人贴的「已通过」都不算；运行期间源码被改了，结果作废重跑。
2. 0 个用例不算通过。看报告里实际执行的用例数，不看「构建成功」。
3. 跑不了就是「未验证」。写明原因，不写成「已通过」。

交付时分开写：改了什么、测试的实际数字、未验证的项、git 状态。读过规则、编译通过、测试通过，三件事不能互相代替。

## 五、git

- 只提交本任务改的具体文件：`git add -- 路径/文件` 或 `git commit -- 路径/文件`。不用 `git add -A` / `git add .` / `git add -u`。
- 不推送。把分支名和提交号告诉我，由我来推。
- 被守卫拦下后，不加 `--no-verify`，不换写法重试。
- 一个子任务一个提交；提交信息写清楚做了什么。
- 不带本地专用的改动：调试日志、本机地址、临时配置。
- 改写历史只限没推送的分支。
- 〔提交身份、提交信息格式等项目约定〕

## 六、沟通

- 〔语言〕，结论先行，简短。
- 能查代码弄清楚的不问我。
- 需要我手工执行的步骤单独醒目列出。
- 不编造我没说过的话；没验证的事不写成已验证。
- 误读了我的意思，主动说明并撤回改动。

## 七、交付前自检

- [ ] 改动的文件都是本任务的吗？有没有超出确认的范围？
- [ ] 规则原文读了吗？硬约束逐条有结论吗？
- [ ] 测试跑了吗？实际执行了多少个用例？没跑的原因写了吗？
- [ ] 有没有需要我手工执行的步骤？单独列出来了吗？
- [ ] 提交里只有本任务的文件吗？
- [ ] 回复里有没有把没验证的事写成已验证？
